# 测试策略

> TDD 的执行循环（RED-GREEN-REFACTOR）见本目录 `engineering-tdd.md`。
> 本文件只补它没覆盖的：**测什么、测到哪层、怎么算达标、什么算假绿**。

## 1. 测试金字塔（按成本与稳定性分配）

```
     /\\        E2E / 端到端（少，关键链路）
    /  \\       集成测试（模块间接线、真实适配器 mock 外部 IO）
   /____\\      单元测试（多，纯逻辑、快、确定性）
```

- 大头放单元测试：纯函数、状态折叠、路由判定、校验逻辑。
- 集成测试专测**接线**：模块 A 的输出是否真被模块 B 消费（对应 architecture-contracts 的断点）。
- E2E 只覆盖少数关键链路；不追求数量，追求"能证明系统真的跑通"。

## 2. Mock 边界（防"fake 自洽"陷阱）

1. **只在系统边界 mock**：网络、进程、时钟、随机源、外部存储——这些必须可注入。
2. **不 mock 被测对象内部的业务逻辑**：否则测的是 mock 而非实现。
3. 生产路径的核心逻辑必须有**非 fake 的测试**；fake 用例只能作为补充。
4. 测试替身（Fake/Stub/Mock/**InMemory/Local/内存版**）不得出现在 `src/`——
   `scan_gaps.py` 扫前缀，`source_purity.py --path src --strict` 扫语义信号（含内存实现/意图注释/文件名），
   后者是硬门禁（见 `source-purity.md`）；测试区自动排除。
5. 真实适配器（HTTP/stdio/DB）要有接线测试：mock 底层 IO，但走真实适配器代码。

## 3. 达标口径（S4 自省的硬指标）

| 项 | 达标条件 | 证据 |
|---|---|---|
| 通过率 | 100% 通过，无 skip / xfail 掩盖 | 测试命令输出（passed 数 = total 数） |
| 红转绿 | 每个实现都有"先红后绿"的失败测试 | TDD 记录 / commit 历史 |
| 覆盖率 | 达到项目阈值（默认 ≥80%，关键路径更高） | `--cov` 报告数字 |
| 关键路径 | 核心逻辑分支全覆盖（含失败分支、异常折叠） | 覆盖率明细 |
| 安全用例 | danger 路由 / 注入拒载 / 缺席拒绝均有用例且绿 | 用例名 + 输出 |
| 接线用例 | 跨模块数据流有集成测试 | 用例名 + 输出 |

## 4. 什么算"假绿"（必须警惕）

- 测试全用 fake，生产路径零覆盖（绿但无意义）。
- skip / xfail 掩盖失败；用例数对但断言被注释掉。
- 覆盖率达标但都是 trivial 代码，核心分支未测。
- 只测正常路径，不测失败/边界/异常折叠。
- 测试依赖真实时间/网络/随机，结果不稳定（flaky）。

## 5. 按语言常用命令（唯一证据来源：verify.py）

见各 `coding-rules-<lang>.md` 的"验证命令"一节，**必须由 `verify.py --lang <lang>` 统一执行**。

**硬纪律（防止"裸跑冒充达标"）**：
- **只认可 `verify.py` 的输出作为 S4 测试证据**——AI 手跑的裸命令（`pytest -q`、`vitest run`、`go test` 不含覆盖率）不算门禁证据，即使全绿也不得写进 overview 的"验证结果"。
- `verify.py` 内置 coverage-gate：命令集里没有覆盖率命令直接 FAIL、退出码非 0。裸跑测试过不了这关。
- **覆盖率阈值二选一**：命令行参数（如 `pytest --cov-fail-under=80`、`cargo llvm-cov --fail-under-lines 80`）**或**项目配置（vitest.config 的 `thresholds`、`coverage.py` 的 `fail_under`、CI 脚本）。配置式阈值必须在本台账里写明配置文件与阈值行号，拿不出即视为未达标。
- 本项目踩过的坑：M04 落地时 AI 手跑 `pytest -q` 得到 144 passed 就宣称自省完成，未跑覆盖率——规则文件里的 `pytest --cov=src --cov-fail-under=80` 被绕过。上述纪律即为堵此漏洞。

## 5.5 真实环境优先（照真实环境写、用真实环境测、环境报错如实上报）

> 与 `architecture-contracts.md` §4.5 同源，此处是测试侧的完整协议。

**原则一 · 照真实环境写代码**
- 实现依赖 DB/Redis/容器/外部 API 的功能时，**代码语义照真实基础设施写**（真 SQL/真协议/真错误语义），
  不是照 fake 的简化行为写——fake 只是单测替身，不是实现模板。
- 无真实环境时功能照做（生产 adapter 进 src/），只是把"只能在真实环境验证"的部分登记为
  「待真实环境验证」未完成项——**禁止砍功能、禁止只写 fake 标完成**（见 architecture-contracts §4.5）。

**原则二 · 测试默认用真实环境**
- 有真实环境依赖的项目，测试**默认跑真实入口**（`env_probe` 给的 `recommended_real_test_cmd`，如
  `tests/integration/`），不是默认跑 mock/unit 那套。unit 是补充，不是默认交付证据。
- S0 跑 `env_probe.py --project-root .`，把 `docker_available`/`real_test_dirs`/`needs_real_env` 写进 overview。
- 用户说"跑真实测试"时，跑真实入口而非复用旧 mock 命令；若暴露功能当初被砍 → 先补实现再验证。

**原则三 · 环境报错如实上报（关键：区分"代码 bug"与"环境缺失"）**

测试报错时，AI 必须先判断根因类别，**不许一律当代码 bug 闷头改，也不许一律跳过**：

| 报错类别 | 判定依据 | 处理 |
|---|---|---|
| **代码 bug** | 逻辑/断言/接线错误，与基础设施是否可用无关 | AI 自己修，改完重跑到绿 |
| **环境缺失** | 连接被拒、容器起不来、缺驱动/依赖、超时等——根因是真实环境不可用 | ① **明确告知用户**："此测试需真实环境（<Docker/DB/...>），当前报错 X，属环境依赖，非代码缺陷"；② 说明 **AI 解决不了**（无法凭空造真实基础设施）；③ 登记为「环境阻断」未完成项，**暂时忽略该项**继续推进其余可验证部分；④ 用户启动环境后回来补跑 |

- **"暂时忽略"的合法条件**：已显式告知用户 + 已在 overview 登记 + 错误确属环境类。三者缺一不可。
- **与"禁止 skip/xfail 掩盖失败"的区别**（见 §3/§4）：那禁止的是**静默**跳过真 bug；这里允许的是
  **显式上报**的环境阻断——一个隐瞒，一个透明，不冲突。绝不能把代码 bug 伪装成"环境问题"来跳过。
- **禁止行为**：把环境报错反复尝试"修"成假绿（改断言、换 fake、加 skip）；或反过来把代码 bug 赖成"环境问题"。

**证据分级**：fake 绿只证明单元逻辑；生产路径的真实消费必须由真实入口测试证明。
环境阻断项在 overview 单独标记，不计入"测试全绿"，也不冒充通过。

## 6. 使用方式

- TDD 阶段：按金字塔选测试层级；边界处注入 fake，核心逻辑写真测试。
- S4 自省：按"达标口径"逐项核对，假绿信号逐条排查；结果写入 overview。
- 拷问代码场景：本文件是"覆盖率/通过率"专项检查的依据。
