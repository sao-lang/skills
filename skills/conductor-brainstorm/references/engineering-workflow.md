# 工程工作流（conductor 内置工程纪律）

> 提取自 obra/superpowers 的 7 步工作流 / 写计划纪律 / 4 条理念，本地化重述（版权归原作者）。
> 目的：让 conductor 成为**单一主控**，不依赖外部 superpowers skill。

## 核心理念（4 条，贯穿全程）

1. **测试驱动**——永远先写测试，没有失败测试不算实现。
2. **系统化优先于临场发挥**——用流程取代猜测。
3. **降低复杂度是首要目标**——简单优于聪明（配合最小改动原则；原 ponytail 已内联）。
4. **证据优于声称**——宣布完成前先验证，拿不出证据不得标完成。

## 7 步基础工作流

七步与 conductor 器官的映射（**只第 1 步归本器官**，其余是别的器官或机体的职责）：

| 步 | 名称 | 归属 | 挂载 |
|---|---|---|---|
| 1 | 头脑风暴 brainstorming | **conductor-brainstorm（本器官）** | 场景链 S2，见下文详解 |

| 3 | 写实施计划 writing-plans | **conductor-brainstorm（本器官）** | 见下文 `plan` 能力详解 |
| 4 | 子代理驱动开发 subagent-driven | conductor 机体编排 + `../../conductor-review/references/independent-review.md` | 不下放为器官；编排权在机体 |

**备选执行模式**：`executing-plans`——分批执行+人工检查点，适合需人在场的场景。

## `brainstorm` 能力详解

### 开口之前先调查
**在已有项目里，或用户给了上下文（规格/计划/交接/指定文件/之前对话）时：先读，再开口**，读到能解释"相关部分现在怎么工作、这次改动会碰到什么"。
- 永远不要问上下文已回答的问题，也不要重开用户已决定的事。
- 规格该知道的都知道 → 直接做并说明；有重要缺失 → 进入澄清对话。

### 第一条消息（one message 规则）
- 用户已说清：约 200 字，用自己话**复述**需求（要什么/给谁/为什么）+ 查到的现状与影响面；发现会改变需求的约束/冲突/更省的路径就直说；结尾邀请纠正。若不知"为什么"，问一个开放问题；若已知，问"哪个未定项最影响要建什么"。
- 用户没说清：问一个聚焦**最大未定项**的开放问题，说明"答案会如何改变要建的东西"。
- 用户没要求头脑风暴：结尾给轻量"也可以直接开做"选项。用户选直接做 → 本能力结束，用一句话说明重大实现方式选择，然后按正常流程做。

### 播放回述
理解一部分就**用 200-300 字复述那部分**（做什么/给谁/某块怎么表现），再问下一部分——复述与提问交替。只把用户说的记为用户说的；你补的标注为提议并给理由。每块结尾问"哪里不对或漏了"。

### 两条关键红旗
| 想法 | 真相 |
|---|---|
| "用户说'听起来不错'＝设计被批准了" | 批准只覆盖展示过的东西；还没写的设计文档**没有被批准** |
| "我填个合理默认值就行" | 可以，但**必须说出来**——用户没听到的默认，就是他无法拒绝的默认 |

其他红灯：别先抛菜单让用户选；别先解释流程；spike 批准后想留着继续做 → 是新请求，重过确认门。

### 设计文档规模
小改动→短文档，项目级→完整文档；都必须有 **Approaches 节**（2-3 种方式、取舍、选了哪个、为什么）。中途变大→停下升级规模；几个独立项目→商定顺序逐个来。

## `plan` 能力详解

计划是给"热情但品味差、没判断力、没项目上下文、讨厌写测试"的初级工程师看的——清楚到照做不跑偏。

### 计划文档头
```
# <功能名> Implementation Plan
**Goal:** <一句话>   **Architecture:** <2-3 句方法>
**Tech Stack:** <关键技术/库>   **Spec:** <本计划实现的设计文档路径>
```

### 任务结构（含 Interfaces 块）
```
### 任务 N：<组件名>
**Files:** - Create: <精确路径> / - Modify: <精确路径:行号> / - Test: <精确路径>
**Interfaces:**
- Consumes: <本任务用到、前面任务产出的东西——精确签名>
- Produces: <后续任务依赖的东西——精确函数名、参数/返回类型>
- [ ] Step 1: 写失败的测试（代码+断言，规格里的精确值）
- [ ] Step 2: 跑测试确认失败（命令+预期失败信息）
- [ ] Step 3: 实现精确签名（签名/测试已决定的部分不写函数体）
- [ ] Step 4: 跑测试确认通过（命令+预期输出）
- [ ] Step 5: Commit（git add 精确文件 + commit message）
```
**Interfaces 块不可省**：implementer 只看自己那段，这是它知道邻近任务用什么名字/类型的唯一途径。精确值只出现在 brief/plan，不靠口头传递。
**步骤粒度**：一步 = implementer 能写出**恰好一个合理的东西**；不要求完整，要求无歧义。

### 硬约束
**YAGNI**（只写被要求的）、**DRY**（重复逻辑抽出但不过度抽象）、**可验证**（每任务有"怎么知道做完了"）、**无歧义**（路径/函数名/改哪几行全写死）。

### Self-Review（写完计划自己跑五问，不派子代理）
1. **规格覆盖**：逐节扫规格，每条要求都能指向一个实现它的任务？列缺口。
2. **步骤扫描**：每步只让实现者写一个合理东西；"决定不了任何事的一行"是缺口，"签名和测试已决定却写满函数体"是程序誊写——都修。
3. **类型一致性**：后面任务用的类型/方法签名/属性名与前面定义一致？（`clearLayers()` vs `clearFullLayers()` 就是 bug）
4. **Review Focus**：规格隐含的每个输入类/失败模式都有测试覆盖？最可能咬人的 5 个未覆盖项写进 Review Focus，每项把测试加进所属任务。空节=查过没有，不是跳过。
5. **篇幅比例**：计划比规格长几倍=誊写了程序；代码块占大头时用签名/测试名/断言替换函数体，同时确认每步仍无歧义。
反例："优化性能""把那块重构好"（无路径/验证/改法）、"TBD""处理边界""加适当校验"（决定不了任何事）。规格要求没任务→补任务。

## 完成前验证
宣布完成前先跑**能证明真的完成**的命令，证据是测试输出/linter 退出码/覆盖率数字，不是感觉。与 conductor 的 S4 门禁（scan_gaps+verify）叠加，不重复造流程。
