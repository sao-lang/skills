# 设计文档规格模板（Design Spec Template）

> 用途：conductor 场景 1/2/3/4 的 `brainstorm` 产出物，也是 S2 `plan` 的 `Spec:` 输入——
> **规格与计划同行**，计划里的每条任务都要能指回本规格的一条编号要求。
> 纪律来源：`brainstorm-plan.md`（Approaches 必备）、`examples-to-spec.md`（样例之外覆盖）、
> `grill-design-SKILL.md`（设计树拷问，每分支必须有结论）。
> 场景契约要求的架构五要素、接线四问等跨器官纪律由 conductor 在 S2 统一编排加载，本文件只提供落位章节。
>
> **规模裁剪**：精简版用 §1/2/3/5/6/10/12；项目级用全节（§8 各子项按涉及程度填，不涉及写"不涉及"）。
> 无论长短，**§1 设计意图、§4 技术栈、§6 Approaches、§10 未决假设都不可省**——这是硬要求。

---

## 文档头（每个规格必须有）

```markdown
# <功能/改动名> 设计规格
**状态**: 待确认 / 已确认        ← 未确认前禁止进入写代码
**范围**: <一句话：要什么 / 给谁 / 为什么>
**技术栈摘要**: <语言 / 核心框架 / 存储，详见 §4>
**关联**: 前置规格 <路径> / 关联代码 <路径> / 来源需求 <链接>
**变更类型**: 新建 / 补充设计 / 重构依据     ← 补充设计时 §13 必填
```

## §1 设计意图（Design Intent）

> 回答"为什么**这样**设计"，不是"为什么做这件事"（那是 §2）。
> 这一节是整份规格的价值锚点：后面所有取舍、Approaches 的选择、架构分层，都要能回溯到这里。

- **一句话意图**：这个设计想守住什么、优先什么。
  例："宁可牺牲一点性能，也要让每条业务规则可独立测试、可单独替换。"
- **设计原则**：3-5 条，每条必须**可判定**（能据此判断某个实现是否违背）。
  反例："高可用、易扩展、性能好"——无法判定，等于没写。
- **价值排序 / 冲突裁决**：当两个目标冲突时先保哪个。
  例：一致性 > 可用性；可测试性 > 代码量；简单 > 灵活。
- **反意图**：明确**不追求**什么，防止实现者跑偏。
  例：不引入泛型抽象层、不做插件机制、不提前支持多租户。
- **与既有设计意图的关系**：沿用 / 改变（改变必须说明理由与影响面）。

## §2 背景与目标

- **现状**：相关部分现在怎么工作（先读代码/文档再写，禁止凭空描述）。
- **动机**：为什么改，不改会怎样。
- **影响面**：这次改动会碰到哪些模块 / 调用链 / 契约 / 文档。
- **成功标准**：一句话说明做完之后系统表现出的可观察差异。

## §3 范围与边界

- **范围内**：列出要做的。
- **范围外**：明确不做的（防止执行时擅自扩大）。
- **反向排除**：什么**不该**被匹配 / 被改变（对应 examples-to-spec 的"反向"维度）。

| 类别 | 选型（含版本） | 选型理由 / 约束 |
|---|---|---|
| 语言 / 运行时 |  |  |
| 核心框架 / 库 |  |  |
| 数据存储 / 中间件 |  |  |
| 构建 / 测试工具 |  |  |
| 部署 / 运行环境 |  |  |

- **既有技术栈约束**：项目已定、不得擅自更换的技术与版本。
- **新增依赖**：列出本次新引入的依赖及其必要性（YAGNI：能不加就不加）。
- **未定项**：→ §10 未决假设（如"ORM 用 A 还是 B 待定"）。

## §5 需求清单（编号、可测、可追溯）

每条要求一个稳定编号，便于 plan 逐条映射、`scan_gaps.py` 逐条核对。

```
- FR-1：<行为要求，含精确值/签名/边界> — 验收：<测试名或命令 + 预期>
- FR-2：...
- NFR-1：<性能/安全/兼容等约束> — 验收：<指标或检查方法>
```

纪律：精确值（数字、枚举、签名、错误码）只写在规格里，不靠口头传递；
禁止"适当校验""处理边界"这类决定不了任何事的表述。

| 方案 | 做法（1-2 句） | 优点 | 取舍 / 代价 | 结论 |
|---|---|---|---|---|
| A |  |  |  | 采用 / 备选 |
| B |  |  |  | 采用 / 备选 |
| C |  |  |  | 采用 / 备选 |

- 至少 2 个方案（项目级 2-3 个），**选了哪个、为什么**必须写明，并回溯 §1 的价值排序。
- 只有一个方案时，说明"考虑过但未采纳的替代"及否决理由——不许静默单选。

## §7 架构设计（项目级必填；小改动只填涉及的部分）

### 7.1 架构总览
一张图（mermaid / ASCII 均可）+ 组件清单。图中每条箭头标清**调用方向**与**数据流向**，
且每个箭头都能在 §5 找到对应要求——画不出来的箭头说明有未登记的需求或断点。

### 7.2 分层与模块职责
按职责隔离，不越界伪造。参考四层模型（按项目实际裁剪）：

- **内核层**：只做编排与纯计算，不 import 上层策略；用结构化投影/鸭子协议解耦。
- **插件层**：只实现 `apply(host)` 挂载；跨调用状态由插件实例自身持有。
- **能力层**：协议 + 默认实现 + 归属 + install 四要素齐全；缺实现须显式登记"待实现"及归属。
- **装配层**：用户未注入时注册默认实例——**此层缺失时其余层"接口就绪"不等于系统可用**。

### 7.3 模块契约
逐模块写清：public API / port 的精确签名、输入与输出、错误语义、归属模块。

### 7.4 数据流
从入口到终点的完整路径，标出每个环节产出的字段由谁消费，形成闭环。

### 7.5 装配入口（composition root）
写明统一装配入口在哪、谁在运行时把各模块接起来——禁止遗漏。

### 7.6 接线四问（设计阶段预填，S4 再逐条核实）
1. 谁调用它？（public API 有无真实调用者）
2. 它调用谁？（依赖的下游 port 是否真被注入）
3. 信号 / 意图被谁消费？（emit 出的 Event / Decision 有无订阅者）
4. 数据流闭环吗？（上游字段有无下游消费者）

## §8 其他关键设计维度（按涉及程度填，不涉及写"不涉及"）

> 这些是规格里最容易被跳过、事后又最常召回的部分。每项回答列出的核心问题即可。

### 8.1 术语与领域模型
统一语言：关键实体、字段、状态的**唯一名称与含义**。跨模块用同一个词指同一个东西——
命名漂移是协议漂移的前兆。

### 8.2 数据与存储
数据从哪来、存到哪、谁读写、生命周期与迁移方式。表结构 / schema 的字段要能追到 §5 的需求。

### 8.3 错误、异常与降级
失败模式清单（不存在 / 无权限 / 超时 / 重复 / 部分失败）、每类的处理策略、
降级路径与 fail-closed 边界。禁止"出错时提示用户"这种无信息量的描述。

### 8.4 依赖与外部集成
依赖哪些外部系统 / 服务 / API；每个依赖的调用点、失败影响、超时与重试策略——
呼应 §7.6 第 2 问"它调用谁"。

### 8.5 可观测性
日志 / 指标 / 告警：关键路径上留什么痕，才能证明"信号被消费了""数据流闭环了"。
这是事后发现功能断点的眼睛。

### 8.6 兼容与迁移
对既有公共契约、数据格式、调用方的影响；升级 / 回滚 / 灰度路径。

## §11 约束与红线

- 安全：密钥脱敏、不可信输入 fail-closed、危险路由、成本闸门；具体红线清单由 conductor 按场景编排安全审查提供，本节只登记结论。
- 兼容：既有公共契约不得破坏（除非规格明确要求）。
- 测试策略：写清行为测试覆盖到哪一层、覆盖率口径；执行由 conductor 在 S3 编排测试器官完成。

## 定稿自检（写完后自己过一遍）

1. **设计意图写了吗？** 有价值排序和反意图，原则可判定——不是"高可用易扩展"这类空话。
2. **技术栈落到名字和版本了吗？** 未定项是否登记进 §10，而非用"通用框架"掩盖。
3. **Approaches 节在吗？** 2-3 个方案 + 取舍 + 选择理由，且选择回溯 §1 的价值排序。
4. **架构图的箭头能对回 FR 吗？** 画不出的箭头 = 未登记的需求或断点。
5. **装配入口写了吗？** 只描述模块不写谁把它们接起来 = 功能断点温床。
6. **未决假设有没有静默默认？** 用户没明确点头的都登记进 §10。
7. **每条要求可测吗？** FR 有精确值和验收方式，没有"适当/合理/处理边界"。
8. **样例补全落地了吗？** 用户举过例子就有 §9，且补全项分类确认过。
9. **可映射吗？** plan 的每条任务都能指回一个 FR 编号；反之每个 FR 都有任务覆盖。
10. **补充设计守边界了吗？** 只补缺口，未重写既有结论，§13 有变更记录。
