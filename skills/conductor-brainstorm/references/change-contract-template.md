# Change contract · 六段模板

> 一份契约 = 一次改动的持久快照。文件名建议 `change-contract.md`，放在项目根目录或 `docs/` 下。
> 规则：只写有后续影响的内容；不写流水账；Acceptance 必须可机器验收。

```markdown
# Change: <ID> / <日期> / <状态：draft|confirmed|verified>
## Why
<这次改动要解决什么。写动机与用户意图，不写方案。>

## Delta
<相对上一版基线的具体变化。首个基线写"首个基线，无前序版本"。
每个条目都要过删除推导：新增/替换了什么，就问它替代/废弃了什么。
删除/替换条目必须用反引号带可核对符号名（函数/类/字段/路径），
格式：`- 删除 \`Xxx\`（因 <新条目> 而消失）`；纯中文描述机器无法核对。>
- 
- 删除 `符号名`（因 <新条目> 而消失）

## Invariants
<不能破坏的既有契约：接口签名、数据格式、错误语义、权限边界。>
- 

## Affected
<可能受影响的模块/符号/调用方 + **受影响的设计文档**（docs/ 下与本改动相关的架构/设计/接口文档路径）。交 conductor 编排影响面核实；文档条目在 S5 收尾时作为文档同步的核对清单。>
- 

## Acceptance
<可机器验收的条目。每条必须能对应一条命令+退出码或文件:行号。>
- 

## Open
<仍未拍板的事项，每条带需谁拍板；被否决的方案也记在这里。
**兼容层/过渡双轨**若获准保留，必须登记在此：谁批准的 + 退出条件（废弃期限或迁移完成判据）。>
- 
```

## 填写口径

- **Why** 不写"加了 X 函数"，写"用户反复遇到 Y，导致 Z"。
- **Delta** 用动词开头：新增 / 删除 / 替换 / 重命名 / 约束。
- **Invariants** 写"不许变"，不写"建议不变"。
- **Affected** 允许是草稿，但必须标注"需 conductor 编排的影响面核实"；**设计文档与代码模块同等登记**——改了公共契约/接口/架构决策却不列文档，S5 文档同步必查项会 FAIL。
- **Acceptance** 禁写"工作正常"，必须写可执行验证。
- **Open** 非空时，conductor 不得把契约标为 confirmed；**兼容层未带退出条件 = 视为未拍板**，阻断 confirmed。
