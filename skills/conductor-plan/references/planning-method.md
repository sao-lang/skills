# 通用路径规划方法

> conductor-plan 的核心方法：把用户输入 + 上下文 → 一张完整执行图。
> 通用引擎，不限开发；被 conductor 调用时加载 conductor 机体的 `references/01-routing/execution-graph-adapter.md` 适配。
> **只规划出图，不执行**——循环/重试/空转的字段写进图，执行由调用方负责。

## 第 1 步：事务分类（先分清哪些是任务、哪些是噪音）

用户输入常夹杂无关内容，先分类，别把闲聊画进流程图：

| 类别 | 处理 |
|---|---|
| **任务相关** | 进图：这是要规划的目标或步骤 |
| **环境杂务**（装依赖/找路径/开权限） | 作为前置 `tool` 节点，或标 `precondition`，不混进主链 |
| **用户闲聊/情绪** | 不进图，回应但不规划 |
| **外部操作**（发邮件/订票/提交代码） | 作为 `action`/`tool` 节点，标注副作用与不可逆性 |
| **历史回指**（“照上次那样”） | 触发习惯适配（第 5 步），不单独成节点 |

## 第 2 步：意图分析（上下文 + 用户输入 + 用户习惯）

回答四问，**答案与措辞无关**：

1. **目标产出物是什么？**（一张图 / 一个决定 / 一个可交付物 / 一个资源状态）
2. **作用在什么对象上？**（代码 / 文档 / 生活事务 / 业务流程 / 决策问题）
3. **约束与偏好？**（时间/工具/详略/用户说了“最小改动”“快一点”“要详细”）
4. **信息够不够出图？**（够→第 3 步；不够→第 2.5 步澄清）

**上下文来源**：当前对话历史、已加载的 overview、用户指定的文件、目录事实（实际 `ls` 不靠猜）、用户历史习惯。

## 第 2.5 步：澄清循环（不清楚就问，等待用户输入）

这是**硬要求**——引擎遇到信息不足必须停下来问，禁止猜着往下画：

1. **识别缺口**：缺关键对象 / 缺产出物定义 / 缺判定条件 / 缺约束 / 有多种合理解法且分叉大。
2. **一次问清一个 frontier**：把相关未决项一次性列出（最多 3-5 个），别挤牙膏式追问。
3. **给候选降低用户成本**：能给 2-3 个选项就让用户输入编号，开放问题说明“答案如何改变图”。
4. **明示假设**：如果用户不答但必须推进，把假设写进 `assumptions[]` 并请用户否决——悄悄假设比明示后被否决更糟。
5. **置信度闸门**：≥0.8 出图；0.5–0.8 声明+请确认；<0.5 必须问，禁止出图。
6. **等待输入**：`ask` 节点输出后暂停，用户回应后从第 1 步重跑（或增量更新图）。

## 第 3 步：拓扑推导（依赖排序，不按说话顺序）

**用户说话顺序 ≠ 执行顺序**。按依赖排：

| 规则 | 说明 |
|---|---|
| 生产者先于消费者 | B 要用 A 的产出 → A 排 B 前（含隐含产出：“根据 M6 改代码”必先有“读懂 M6”） |
| 销毁操作最后 | 删除/覆盖/移动的资源若被别的节点用 → 排到所有消费者之后 |
| 闸门内联 | 前段产出喂后段时，中间插 `gate` 校验，不凭空衔接 |
| 改码必带验证 | 有改码段 → 后面必须有验证 gate（“验证通过”作为后续销毁/发布的前置） |
| 失败路径显式 | 每个可能失败的关键步骤标 `on_fail`（ask/retry/abort/skip），不留隐式崩溃 |

**拓扑类型**：单节点 / 链 / 分支 / 并行 / 循环 / 嵌套（subplan）。复杂任务用 subplan 分层，别画成一张巨型图。

## 第 4 步：步骤展开（始终完整展开到动作级）

用户要求：**始终完整展开**——每个节点必须明确到“做什么、谁做、怎么算完成”：

1. **动作类型**（kind）按 schema 六类叶子选：`tool` / `skill` / `research` / `think` / `ask` / `gate`（通用场景加 `action`）。
2. **action 字段**写具体：工具名+参数 / 读哪个文件 / 判断什么条件，禁止“处理一下”“优化优化”这种决定不了任何事的描述。
3. **exit_criteria** 必须可判定：命令退出码 / 文件内容 / 用户确认 / 判定结果。无退出判据的节点校验器会 FAIL。
4. **inputs/outputs** 写明节点间传递的契约（前产出喂后输入），互不衔接的节点别硬连边。
5. **粒度**：一步 = 执行方能“恰好做出一个合理东西”；不要求写完整实现，要求无歧义。
6. **空转防护**：给循环/重试节点定 `budget.max_rounds` 和 `noop_limit`；给每步定退出判据——执行方检测连续无变化则停。
7. **Self-Review**：出图后自己跑五问——目标覆盖（每个意图有节点）？步骤可判定？依赖正确？失败路径全？无冗余/空转节点？不过就修。

## 第 5 步：习惯适配（用户偏好）

从上下文和历史推断，写到图的 `meta.habit_refs`：

- 用户历史选择（详略、工具偏好、是否爱子代理、是否要 commit）
- 反复出现的约束（“别用 Any”“最小改动”“先别提交”）
- 本次显式偏好优先级 > 历史习惯 > 默认

**“照上次那样”**：读 overview/历史图的 `meta.habit_refs` 和最近一张执行图，复用其节点粒度与工具选择，只替换本次目标与对象。

## 第 6 步：出图与固化

1. 按 `execution-graph-schema.md` 生成 JSON（唯一真相源）。
2. 生成 mermaid 图给用户看（flowchart；控制流用 subgraph/判定节点；循环用回边）。
3. 输出自然语言声明：目标 / 模式 / 节点数 / 关键分支 / 置信度 / 假设 / 省掉 / “错了请说”。
4. 固化路径：`standalone` → overview 旁或用户指定；`conductor` → overview 的执行图节，S1 声明引用。
5. 跑 `plan_validate.py` 校验：结构合法 + 无空转漏洞 + mermaid 可生成；不过则修图重出。

## 降级

- 信息不足且用户未回应 → 停在 `ask` 状态，**不出图**，禁止猜着画完整流程图。
- 模板匹配不上 → 用 generic 模板从零推导，不硬塞场景。
- 图太复杂（>30 节点）→ 拆 subplan 分层，别出巨型图。
- 校验器不可用 → 人工按 schema 第七节逐条核对，声明“未机器校验”。

## 边界

- 本器官**只规划出图**：循环/重试/空转的检测字段写进图，实际执行与状态跟踪由调用方（conductor 或用户/agent）负责。
- 被 conductor 调用时，动作类型与门禁复用 conductor 的器官/脚本（见 conductor 机体的 `references/01-routing/execution-graph-adapter.md`）；standalone 时用通用动作类型。
