# 规划反例库（真实失败案例）

> 用途：规划前扫一眼本库，避免重犯同类错误。每条 = 用户原句 → 错误解析 → 正确解析 → 根因 → 防线。
> 本库只记录**规划层的判断失误**（不记录代码 bug），由 conductor-plan 持有。

## 案例 1：并列任务被合并成单节点，改码任务被吞

**用户原句**（跨两轮，第二轮为触发句）：
> 轮1：①补充场景，需先落方案；②`_l1_rule_intent` 是已写完的代码，需扩充里面的词表。
> 轮2："前面补充场景的问题，先落方案文档，可能要修改现在的方案文档，_l1_rule_intent 去类型化，此表还需要再扩大，要覆盖大部分场景，命中用户在生成手机widget时候的大部分意图，你可以往这方向调研一下，看看扩大到什么范围更好。"

**AI 的实际路由（错误）**：
单节点，场景3补充设计/文档路径，full，置信 0.85，声明"不改码"；
把"三路调研"挂在"补充场景落文档"下，称为落方案前置；省掉 TDD/verify/source_purity。

**正确解析**：
这是**两个并行的原子任务**：
- 任务 A（文档）：补充场景 → 落/改方案文档 → 场景3，文档路径
- 任务 B（改码）：`_l1_rule_intent` 去类型化 + 词表扩大覆盖手机 widget 意图 → 场景5/6，改码路径
  - 前置：`research` 调研范围（serves_task=B），不是 A 的前置
  - 后续：TDD（去类型化需测试守护）→ verify → review → 收尾
- 两任务无依赖 → 建两个并列 subplan，**派两个子代理**（≥2 独立大任务）

**五层失守与防线**：

| 层 | 错误 | 防线（已修） |
|---|---|---|
| 结构抽取 | 逗号并列两宾语没识别为并行 | planning-core §1.5 加"并列宾语+动作=并行"算子 |
| 原子意图 | 三问只问一次，被"方案文档"一个产出物覆盖 | planning-core §2.0 原子任务切分（前置层0），每任务各问一次 |
| 消歧 | "去类型化/扩词表"是改码信号却被文档词盖过 | planning-core §2.0.2 锚点：作用于已有代码对象的动作 → 必改码 |
| 计划构建 | 调研挂错消费者（给 A 而不是 B） | planning-method §3 调研归属规则 + schema `serves_task` 字段 + plan_validate 校验 |
| 派发 | 恰好 2 任务落入"≤2 不派" | conductor-subagent 判据改"≥2 独立大任务可派" |

**通用教训**：
1. **字面词 ≠ 意图**——必须结合上下文（宾语是已有代码还是新文档？）推断，抓到第一个锚点就停 = 漏任务。
2. **一句多任务先切再判**——逗号/分号并列宾语、回指历史任务+新任务，都是切分信号。
3. **调研/分析必须挂到它界定的任务**——禁止跨任务借用，写进 `serves_task` 由机器校验。
4. **并列无依赖 = 并行可派**——数量不是派发阈值，独立性与工作量才是。
