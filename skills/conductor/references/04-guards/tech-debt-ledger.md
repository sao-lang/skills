# 技术债台账 · 登记与量化

> 用途：把散落的债标记与已知欠账收敛成一份可量化、可追踪的台账，作为排期与收尾依据。
> 纪律来源：SKILL.md 铁律第 4 条（拿不出证据不得标完成）、overview 纪律第 5 条（未完成项必列）。
> 定位：按需加载（S4 自省 / S5 收尾 / 技术债治理场景触发）。

## 核心认知

- **债不是免死金牌**：登记技术债 ≠ 允许放行。凡以"技术债"名义静默跳过门禁的，一律视为违规（见 SKILL.md 锁 1–4 的例外条款：必须显式声明并记入 overview）。
- **不登记才可怕**：未写入台账的欠账会在交接中丢失，下次会话当"新发现"重复踩。登记是为了让它可见、可排期、可勾销。
- **可量化才可比较**：用「债指数」而非"感觉欠了很多"，才能对比趋势、决定先还哪笔。

## 两个来源

1. **代码内标记**：`TODO` / `FIXME` / `HACK` / `XXX` / `DEBT` / `SAFETY`，运行 `scripts/debt_ledger.py` 得草稿。
2. **overview 未完成项**：各轮 overview 的「L0 未完成项」+「L1 未完成项与下一步」里未关闭的 failure / 缺口，人工并入台账。

## 债指数（量化口径）

按标记权重求和：`FIXME`/`SAFETY` = 3，`HACK`/`XXX` = 2，`TODO`/`DEBT` = 1。
- 报告总量与「热点文件」（债最集中处），用于定位重灾区与横向对比。
- CI 卡口：`--fail-over <N>` 债指数超阈值即退出码 1（可选，默认不卡）。

## 台账字段（每条债必填）

| 字段 | 说明 |
|---|---|
| 位置 | `文件:行号`（拿不出行号只登记不虚标完成） |
| 类型 | 上述 6 类之一 |
| 影响面 | 影响哪些功能/模块，被谁依赖（用 impact_analysis.py 辅助） |
| 优先级 | 高/中/低——安全与数据丢失类默认高 |
| 利息 | 不还会怎样（故障概率、维护成本、阻塞了什么） |
| 勾销条件 | 什么条件下这笔债算还清（可验证） |

## 工作流

1. S4 自省：`debt_ledger.py` 出草稿 → 逐条核对影响面与优先级（静态标记有误报）。
2. 合并 overview 未完成项，按上表补齐字段，写入 overview「L1 技术债台账」段（>30 行独立成 `.debts.md`，主文件只留路径）。
3. S5 收尾：把未关闭的债同步进 L0「未完成项」（≤3 条，超出写"详见 L1"）与 handoff，确保跨会话不丢。
4. 偿还后：勾销条件达成 → 从台账移除并记勾销证据；禁止无声删除。

## 与其他脚本的分工

- `scan_gaps.py` 查"约定违反"（fake 冒充实现、门面无后端、装配断点）。
- `debt_ledger.py` 查"显式标记的债 + 量化"。
- `impact_analysis.py` 查"改动波及谁"，用于评估债的影响面。
- 三者都是草稿，互不替代，结果统一进 overview。
