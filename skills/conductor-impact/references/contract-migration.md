# 接口契约与迁移守卫 · 检查清单

> 用途：在接口（OpenAPI/protobuf/类型定义）与实现之间、在数据库迁移前后，
> 抓住"签名漂移"与"不可逆变更"这两类高发生产事故。
> 定位：按需加载——场景 4/5/6（开发/迭代/重构）涉及接口变更、场景 12 门禁、S4 安全与接线核对时读。

## 核心认知

AI 改接口时最常犯两类错：
1. **契约漂移**：改了实现没改契约，或反之，编译/单测全绿但调用方按旧契约崩。
2. **迁移不可逆**：写了破坏性 DB migration，回滚路径不存在或会丢数据。

两者都不是"测试全绿"能发现的，必须专项核对。

## 一、接口契约漂移检查（改接口必做）

对每一个改动的接口，逐条核对：

1. **四同步**：协议定义（OpenAPI/protobuf/GraphQL schema）、服务端实现、客户端类型、文档/示例——四处签名一致。
   - 证据：贴出四处对应行号，缺一处即"漂移"。
2. **兼容性判定**：本次改动是 breaking 还是 additive？
   - breaking（删字段/改类型/改必填/改语义）→ 必须走版本化（新版本号或新 endpoint），禁止原地改。
   - additive（加可选字段/加 endpoint）→ 确认旧客户端不受影响。
3. **调用方全覆盖**：用 `impact_analysis.py --symbols <接口名>` 找出所有调用方，确认同步更新或兼容。
4. **错误契约**：错误码/异常结构也在契约内，改动需同步（别只顾成功路径）。
5. **契约测试**：有 consumer-driven contract（Pact 等）或 schema 校验测试的，必须跑并绿；没有的， Breaking 改动禁止放行，先补。

## 二、数据库迁移守卫（写 migration 必做）

每条 migration 逐项核对：

| 检查项 | 红线 / 要求 |
|---|---|
| 可逆性 | 必须写 `down`/回滚脚本；无法自动回滚的须显式声明人工回滚预案 |
| 数据丢失 | DROP 列/表、改窄类型、加 NOT NULL 无默认值——逐一确认数据去向或迁移脚本 |
| 锁表与长时间运行 | 大表加索引/改列是否锁表？是否需要在线 DDL / 分批 / 低峰执行 |
| 向后兼容 | 采用 expand-migrate-contract 三阶段：先加新字段兼容旧代码 → 数据迁移 → 再删旧字段；禁止一步删 |
| 幂等性 | 重复执行是否安全（有 IF EXISTS / 幂等标记） |
| 事务边界 | 多步迁移是否在事务内，失败能否整体回滚 |
| 生产验证 | 在含真实数据量的暂存库演练过，记录耗时与锁情况 |

## 三、完成判定（拿证据才标完成）

- 接口改动：四处签名一致的行号证据 + 调用方清单 + 兼容性判定结论。
- DB 迁移：回滚脚本路径 + 数据丢失核对表 + 暂存演练结果。
- 任一红线未过 → 不得标完成、不得收尾；退出码/行号证据写入 overview「验证结果」。

> 提醒：本清单是人工核对清单，不自动执行。静态检查只能提示，最终判定靠证据。
