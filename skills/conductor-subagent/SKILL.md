# conductor-subagent · 子代理派发器官

> **器官类型**：派发（外包车间） —— 输入任务 brief → 输出子代理结果 + 评审/复核结论
> conductor 机体的"外包车间"：主上下文只当调度台，重活派给干净上下文的子代理。
> **不限场景**：只要任务能拆成独立、自包含、可验证的单元——改码、调研、分析、文档、审查都适用。
> **条件触发，AI 看着选**：派发省上下文但费 token，不达标不派；派与不派都必须写进路由声明。

## 输入

- 可拆分的任务集：实施计划（含精确路径与验证步骤）、调研问题清单、批量分析目标、多文档/多模块产出要求等
- 当前上下文状态：已完成的任务数、会话长度、任务间耦合度

## 输出

- 每个被派发任务的：任务 brief + 子代理执行结果 + 评审/复核结论
- 主上下文里只留：每个任务一行结论（通过/返修原因），不留子代理过程

## 派发判据（先判，再动手）

**派**（任一命中且无跳过条件冲突）：
- **≥2 个相互独立**的单元，且每个都是**有实际工作量的大任务**（各自有明确的产出定义与验证方式）——**任务独立性与工作量**优先于数量：2 个大任务并行派发的收益 > 3 个碎任务
- 用户原句/上下文含**并列多任务**（两个独立宾语+各自动作），无生产-消费依赖 → 各自派一个子代理（见 conductor-plan cases.md）
- 多文件/多目标改动，任务间只通过显式契约衔接（改码=Interfaces 块；非码=输入材料清单），无隐含上下文依赖
- 会话已长（前面任务多），继续主上下文直做会污染后面对话质量
- 各任务并行无写冲突（不同文件/不同主题/只读类任务）

**不派**（任一命中即主上下文直做）：
- **单一小改动**，或任务数 ≤2 **且都是琐碎小任务**（派发开销 > 收益）——注意：2 个独立大任务**不在**此项，应派
- 任务紧耦合：下一个任务必须看到上一个任务的完整实现/结论细节才能做
- 强依赖跨任务上下文联想的任务（如根因探索、全局架构权衡）：子代理干净上下文反而丢线索
- 用户明确说"快点 / 别派子代理 / 直接写"

判据冲突时从严（多派），但**每次派与不派都写进声明**：`子代理：派（5 任务独立）/ 不派（紧耦合）`。

## 执行

1. 按序（或并行，前提是无写冲突）派发；每个任务派**全新上下文**子代理，禁止复用旧子代理或旧报告。
2. **任务 brief 必须自包含**：该任务的产出定义 / 输入材料 / 完成标准原文 + 验证方式。
   子代理只看 brief 和必要的输入材料，看不到主对话——brief 里没有的等于不存在。
3. 子代理完成后按任务类型复核：
   - **改码**：两段评审——先查规格符合度，再查代码质量；Critical/Blocker → 返修后**重派新子代理**复审。
   - **非码**（调研/分析/文档）：核对结论正确性（抽查证据源）与覆盖完整性（对照 brief 逐条勾销）；缺漏 → 补 brief 重派。
   评审与复核的完整规则由 conductor 编排对应器官提供，本器官不重复定义。
4. 主上下文只记录一行结论；完整过程留在子代理，不回灌。

## 降级

- 无子代理能力（宿主不支持）→ 主上下文直做，写明「缺子代理 / 影响=上下文占用高 / 降级=直做+更频繁 self-check」。
- 子代理产出不可信（连续返修 ≥2 轮）→ 停下问用户，不要无限派发烧 token。

## 本器官自带（可独立工作）

- `SKILL.md`：派发判据、I/O、执行与降级
- `references/dispatch.md`：brief 模板与防污染纪律
- `scripts/`：无（派发是编排行为，由宿主执行）
