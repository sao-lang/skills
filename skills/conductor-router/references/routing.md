# 场景路由判定（规划器）

> S1 使用。**核心认知：路由不是"匹配场景"，是"规划执行图"**——用户一句话描述的是执行计划
> （节点=场景，边=链/分支，模式=路径），不是单个标签。
> 分工：**有限结构算子用规则匹配**（§1.5）；**无限业务语义交给语义理解**（§2）；
> 不确定性靠"假设明示+置信度+可纠正"兜底；失败降级到只读，绝不猜改码场景。
> **未声明不推进**。

## 1. 判定流程（五层管线）

| 层 | 做什么 | 规则 |
|---|---|---|
| 前置 | 显式场景名 | 用户直接点名场景 → 最高优先，跳过规划 |
| 1 | 结构抽取 | 识别§1.5 算子 → 计划拓扑（单节点/链/分支/并行） |
| 2 | 原子意图 | 每节点用语义三问（§2）定场景+路径 |
| 3 | 计划构建 | 用 scenarios.md 的 I/O 契约校验节点衔接，不符则停下问 |
| 4 | 不确定性 | 输出置信度+假设[]+待澄清[]，假设必须明示供否决 |
| 5 | 确认闸门 | 高执行/中确认/低问；每节点完成后重规划后续是否仍适用 |

## 1.5 结构算子表（唯一需枚举的东西）

业务词汇无限，表达**意图结构**的词极少且稳定。只枚举算子定拓扑；业务语义走 §2。

| 算子 | 信号（有限稳定） | 拓扑 | 处理 |
|---|---|---|---|
| 顺序 | 先/然后/再/接着/之后 | 链 A→B→C | 逐段建节点，前段产出喂后段（I/O 契约校验） |
| 条件 | 的话/如果/要是/否则/不行就 | 分支 cond? B : skip | 条件成立后再定场景（依赖前段产出） |
| 否定 | 不要/只/别/不用 | 排除 | 从候选场景排除被否定路径 |
| 并行 | 同时/分别/都/两个都 | 多实例 | 同一场景作用多对象，或并列多场景 |
| 回指 | 它/这个/上面那个/刚才的 | 上下文依赖 | 读 overview/handoff 消解，消解不了则问 |

> 无算子=单节点（最常见）；算子组合按出现顺序叠加。匹配靠语义（"完了再说"也是顺序），此表是锚点非穷举。

## 2. 语义三问（核心判定法，替代关键词）

对任何说法回答三个抽象问题——**答案与措辞无关**：

1. **想要什么产出物？**（定路径）：问题清单/代码地图/根因台账/评估报告→只读；可运行代码→改码；同步后文档→文档；门禁报告/覆盖率→验证；**删除/归档/整理后的资源状态→清理（文档路径轻量变体）**。
2. **动作作用在什么对象上？**（定场景族）：设计方案→2/3/9；代码结构→7/10；具体功能→4/5/6；故障→8；文档内容一致性→11；**文档/资源的存在性与位置→14**；测试→13；交付→12。
3. **有没有时序结构？**（定场景链，见 §3.5）：有先后→建链，逐段再走前两问。

**泛化示例**（说法不同、三问相同→同场景）：
- "看看 M4 靠不靠谱"/"M4 设计有没有坑"/"审一遍 M4 设计" → 产出物=问题清单，对象=设计 → 场景 9。
- "这模块怎么跑的"/"接手先搞懂"/"理一下调用" → 产出物=代码地图，对象=代码结构 → 场景 10。

## 2.1 意图锚点表（语义交叉验证，非逐行匹配）

先走 §2 语义三问，表只用于交叉验证：语义判出的场景能否在表里找到意图族；找不到**不强行塞入**，提高待澄清置信度。

| 意图族（语义非字面） | 上下文条件 | → 场景 |
|---|---|---|
| 从零建项目骨架 | 代码库为空 | 1 |
| 为系统定架构/分层/选型（产出规格） | 无架构文档 | 2 |
| 在既有设计上补未决分支 | 已有设计文档 | 3 |
| 新增功能（从无到有） | 项目已存在 | 4 |
| 调整既有功能（非故障） | 无明确 bug 现象 | 5 |
| 依新/补充设计改代码 | 有新设计输入 | 6 |
| 改善代码结构（无新设计） | 只为降复杂度 | 7 |
| 排除具体故障 | 有错误现象 | 8 |
| 评估设计/代码质量与遗漏（只要结论） | 只读不改 | 9 |
| 搞懂结构与调用关系 | 只读理解 | 10 |
| 让文档/注释与代码一致（含补注释/修 docstring） | 只改说明文字不改行为 | 11 |
| 删除/归档/移动文档或资源、改与代码无关的文档内容 | 对象是资源的存在性/位置或纯内容，不涉及代码一致性 | 14 |
| 交付前全面检查 | 准备合并/发布 | 12 |
| 为已有代码补测试 | 代码在、测试缺 | 13 |
| **以上都不匹配** | — | **提高待澄清，低置信问用户** |

## 2.2 路径判定（S1 必输出，决定后续阶段）

场景判完立即判路径，详见 scenarios.md 的"场景 × 阶段矩阵"。

| 路径 | 适用场景 | 后续阶段 |
|---|---|---|
| 改码 | 1、4、5、6、7、8 | S2→S3→S4→S5 全程 |
| 只读 | 9、10 | S1→只读分析→写 overview→**结束** |
| 文档 | 2、3、11 | S2(核差异)→S3'(只改文档)→S4(核签名)→S5 |
| 文档·清理变体 | 14 | S1→确认无消费者依赖该资源→执行清理→写 overview→**结束**；无代码改动，不跑 TDD/verify/独立 review |
| 验证 | 12、13 | 跳过新功能设计→S4→S5 |

> 路径判错比场景判错更隐蔽：只读任务走改码路径会硬跑 TDD/verify，空转且误触门禁。

## 2.3 成本档位判定（S1 与路径同时输出）

路径决定"走哪些阶段"，档位决定"每阶段跑多深"——两者正交，都要写进声明。
三档 lite / standard / full 的判定条件、裁剪表、不可裁底线见 `cost-tiers.md`；本处只给判定顺序：

1. 先看 high 条件（多模块 / 架构或迁移 / 跨模块契约 / 隐含清单 / 真实环境新功能 / 用户要零遗漏）→ 命中即 full。
2. 再看 lite 条件（单文件 ≤30 行、无跨模块契约、无隐含清单、本地可验证、置信度 ≥0.8）→ 全中才 lite；用户说"省积分/快一点"时优先走这一步。
3. 其余一律 standard（默认档）。执行中任一条件被打破 → 停下改声明升档，禁止沿用低档省略的步骤补跑当没事。

**声明义务**：必须写出 `成本档位` 与 `省掉：<列表或无>`；lite 可用一行式，见 `cost-tiers.md` §3。

## 3. 上下文消歧（按事实与产出物，不按用词）

1. **设计的三种产出**：要架构规格→2；补未决分支→3；只要评估意见→9。看"要文档增量还是问题清单"。
2. **重构分两种**：带新设计输入→6；只降复杂度→7。看"设计变了没"。
   - **迁移信号**：迁移/搬迁/换架构/重写但"行为要走等价、别漏模块/功能"→7（主线已定、不新增设计），走迁移台账守卫；
     若同时给了新设计规格→6。关键看"是否要求行为等价 + 已定主线"，是则 7，别误判成场景4 新开发。
3. **迭代 vs 解 bug**：有明确故障（报错栈/行为不符）→8；只是增强调整→5。看"是否有故障事实"。
4. **初始化 vs 开发**：看代码库有无骨架——实际 `ls`，不靠词猜。
5. **理解 vs 拷问**：产出地图→10；产出问题清单→9。
6. **补测试 vs 开发**：代码已在只缺测试→13；功能要新建→4。
7. **补注释 vs 迭代**：只改说明文字、行为不变→11（不跑 TDD、不触发独立 review）；改了行为→5。
8. **文档清理/整理 vs 文档同步(11)**：删除/归档/移动、或改与代码一致性无关的文档内容→14；让文档去对齐代码签名/行为→11。看"对象是资源本身还是文档内容的一致性"。
9. **销毁动作在链中的位置**：删除/移动某资源，若链中其他动作要用它→按 §3.5 时序推导把销毁排到最后，不按字面顺序。

消歧用**事实和产出物**说话：查目录、查设计文档、查是否有新设计输入、查报错栈、查代码是否已存在。措辞只作语义线索，不作判定依据。

## 3.5 场景链（一句话多个动作）

用户一句话常含多个动作（"先…然后…""删除X，根据X改代码"）。此时解析出**执行计划**，逐段判场景+路径。

### 切分：先按动作拆，别只盯顺序词

1. 拆出每个**独立动作**（动词+宾语），不只靠"先/然后"——**没有顺序词也可能是链**（如"删除 M6 文档，根据 M6 文档改代码"）。
2. 每段独立判场景+路径（各段路径可不同，常见只读段→改码段→清理段）。
3. 拆不出或对象指代不清（它/这个）→ 读 overview/handoff 消解，仍不清则问用户。

### 时序推导：按依赖排序，不按字面顺序（关键）

**用户说话的顺序 ≠ 执行顺序。** 排时序看**依赖关系**，不看动词出现先后：

| 规则 | 说明 |
|---|---|
| 生产者先于消费者 | 动作 B 要读/用动作 A 的产出 → A 排在 B 前（含隐含产出：要"根据 M6 改代码"，必先有"读懂 M6"这一步，哪怕用户没说） |
| **销毁操作最后** | 删除/覆盖/移动某资源，而其他动作要**用这个资源** → 销毁动作必须排到所有消费者之后（删了就没法读了） |
| 闸门内联 | 用前段产出做后段输入时，中间插一个闸门校验（契约匹配/设计问题已解决/验证已过），不凭空衔接 |
| 改码必带验证 | 链里有改码段 → 其后必须有 S4 验证段，"验证通过"作为后续销毁/发布动作的闸门 |

**示例（销毁依赖资源）**："删除 M6 的文档，根据 M6 的文档先改代码"
- 字面顺序是"删除→改代码"，但删除会毁掉改代码要读的 M6 文档 → **按依赖重排**。
- 正确链路：
  1. 通读 M6 文档（只读→场景10，产出对 M6 的理解/要点）——**隐含步骤，用户没明说但必须补**
  2. 根据 M6 改代码（改码→场景6 设计驱动重构，输入=①的理解）
  3. 验证代码（验证→S4 门禁全绿；改码段必带）
  4. 删除 M6 文档（场景14 清理，闸门=③已通过；排最后）
- 声明里必须把这个重排**显式讲出来**并让用户确认："你虽先提删除，但 M6 文档是改代码的输入，我按依赖把它排到最后执行。"

**示例（设计闸门）**："先检查 M4 设计是否完整，然后根据设计写代码" = 场景9（只读，产出设计问题清单）→ 设计闸门（问题未解决禁止写码）→ 场景6（改码）。

### 链内闸门（否则链式执行无意义）

- 前段产出写入 overview，后段开始先读取，不得无视从零开始。
- 只读段结束不自动进改码段；遇闸门或需用户决策停下问。
- 每节点完成后**重规划**后续是否仍适用（见 §5）。

## 4. 结构化路由决策 + 置信度分级

判定结果用**固定结构**输出（内部思考即可，声明必须含这些字段）：

```
路由决策（执行计划）：
  拓扑: 单节点/链/分支/并行        ← §1.5 算子得出
  节点: [{场景:N, 路径:改码/只读/文档/验证, 档位:lite/standard/full, 输入契约:..., 输出契约:...}, ...]
  边:   [{from:①, to:②, 类型:顺序/条件, 闸门:...}, ...]
  置信度: 0.0~1.0   ← 必填，逼 AI 自查把握
  假设: [<需用户否决的假设>]   ← 无则写"无"
  依据: <语义三问答案+命中算子，不是"出现了某词">
  待澄清: [<不清楚的点>]   ← 无则写"无"
```

**假设明示**：必须做假设才能定场景/路径时（如"M5 是设计还是代码"未说），写进 `假设[]` 请用户否决——悄悄猜对比明示后被否决更糟（用户没纠错入口）。例：`假设:["M5 指设计文档（因'靠不靠谱'多用于评设计）；若指代码请说一声"]`。

| 置信度 | 处理 |
|---|---|
| 高 ≥0.8 | 按声明直接执行，仍声明"错了请说" |
| 中 0.5–0.8 | 声明判断+依据，**请用户顺手确认**后推进 |
| 低 <0.5 | **必须提问澄清**，给 2–3 候选让用户选，禁止猜一个往下跑 |

> 模糊时宁可给低分问用户——问一句的成本远低于跑错一整轮。

## 4.5 路由声明模板（判定后必须先说，用户可纠正）

单场景：
```
我判断本轮走【场景 N：<名称>】，路径【改码/只读/文档/验证】，成本档位【lite/standard/full】，置信度【X.X】。
依据（语义）：产出物=<...>，对象=<...>，结构算子=<无/顺序/条件/...>。
假设：<需你否决的假设，无则"无">   ← 有假设必须请用户确认
将走阶段：<S0/S1/... 或"只读分析后结束">；加载 skill：<列表>；脚本：<列表>；省掉：<步骤列表或无>。
本轮禁止：<禁止项>；下一站：<预期切换>。
如判断有误，直接说"这是场景 X"或"这是只读路径"，我立即重路由。
```
场景链/分支/并行（多节点）：
```
我识别到执行计划，拓扑【链/分支/并行】，置信度【X.X】：
  ①【场景 N】路径【...】档位【...】→ 输出契约：<...>
  ②【场景 M】路径【...】档位【...】→ 输入契约：<...> ← 校验与①输出匹配
边/闸门：<顺序 or 条件 cond? → 校验通过才能推进>；假设：<...>；待澄清：<...>；省掉：<步骤列表或无>。
若置信度<0.8 或契约不符：请确认计划；闸门未过停下问。
每节点完成后重新评估后续节点是否仍适用（重规划）。
```

用户纠正（如"不对，这是解 bug"）→立即重路由重声明，不辩解、不沿用错误上下文。这是最终保障——即使语义判断偶尔出错，一句话就能拉回。

## 5. 场景切换与重规划

- 需求常跨场景（设计→补充→开发→拷问→重构）。**每轮开始路由一次**，阶段跃迁时**重新声明**新场景，切换写入 overview。
- 拷问场景(9)只读，产出的问题清单是下一场景输入，不自动执行修复。
- **执行中重规划**：每节点完成后重评后续是否仍适用——若前段产出超预期（如拷问发现目标模块不存在、问题类型变了），停下重规划，禁止硬着头皮按原计划走（计划基于路由时的信息，执行中信息会变）。

## 6. 判定纪律

1. 猜错场景后面全错；问一句成本远低于跑错一整轮。
2. **声明不可省略**——"未声明不推进"是 S1 硬出口。
3. 用户显式声明 > 一切推断；用户纠正立即生效。
4. 判不出一律归"兜底问用户"，不硬塞场景。
5. **失败降级到只读**：匹配不上、置信度低且用户未回应时降级到场景 9/10（危害最小，最多浪费一轮），**绝不猜改码场景硬跑**。
6. **假设必须明示**并请用户否决，禁止悄悄假设。
7. **契约不符就停**：链式组合前段输出与后段输入不匹配→停下问用户，不硬拼。
